# seoUtils

Утилитарный модуль `src/utils/seoUtils.ts` для управления SEO-данными в многоязычном приложении на Vue 3. SEO-данные загружаются через API-запросы (в разработке — из статических JSON-файлов `public/api/v1/seo/`), а не из переводов Vue I18n. Перед записью в документ все строки проходят санитайзинг (`toPlainText` из `src/utils/sanitizeUtils.ts`).

## Обзор

Модуль получает SEO-данные для текущего языка интерфейса и применяет их к документу:

| Элемент документа           | Источник данных                           | Максимальная длина |
| --------------------------- | ----------------------------------------- | ------------------ |
| `document.title`            | поле `seo.title` из ответа API            | 200 символов       |
| `<meta name="description">` | поле `seo.description` из ответа API      | 500 символов       |
| `<meta name="keywords">`    | поле `seo.keywords` из ответа API         | 500 символов       |
| `<html lang="">`            | текущая локаль `i18n.global.locale.value` | —                  |

Строки перед записью приводятся к безопасному однострочному виду (см. [Санитайзинг значений](#санитайзинг-значений)), а затем обрезаются до указанной длины.

Главное преимущество подхода: SEO-тексты хранятся на стороне сервера, и контент-менеджеры могут менять их без участия разработчиков и без пересборки фронтенда. (При использовании моков из `public/` изменения попадают в сборку вместе с остальными статическими файлами, поэтому пересборка нужна. С реальным API она не требуется.)

> **Важно.** Данные запрашиваются уже после запуска JavaScript. Пользователь и Googlebot (он исполняет JS) увидят актуальные теги, а боты, которые JavaScript не выполняют (в том числе краулеры соцсетей и мессенджеров, строящие превью ссылок), получат только значения из `index.html`. Подробнее — в разделе [Ограничения и особенности](#ограничения-и-особенности).

## Как это работает

1. Пользователь открывает приложение или переключает язык.
2. `setLocale()` в `src/i18n.ts` устанавливает новую локаль и вызывает `updateSEO()`.
3. `updateSEO()` через `fetchSeo()` запрашивает `<base>api/v1/seo/{locale}.json`. Запрос выполняет общий слой `apiGet` из `apiUtils`.
4. Общий слой проверяет статус ответа, что тело ответа является объектом и что поле `language` совпадает с текущей локалью.
5. `fetchSeo()` дополнительно проверяет, что в ответе есть блок `seo`.
6. Внутренняя функция `applySeo()` пропускает каждое значение через `toPlainText`, записывает результат в `document.title` и мета-теги (через `updateMetaTag`), а атрибут `lang` синхронизирует с текущей локалью.

## Импорт и зависимости

```typescript
import { updateSEO, fetchSeo } from "@/utils/seoUtils";
```

Экспортируются только две функции: `updateSEO` и `fetchSeo`. Функции `updateMetaTag` и `applySeo`, а также типы `SeoItem` и `SeoResponse` внутренние и наружу не экспортируются.

Модуль зависит от:

- `apiUtils` — выполнение HTTP-запросов (`apiGet`) и общий контракт ответа (тип `ApiResponse`, в котором есть `language: AvailableLocale`);
- `sanitizeUtils` — санитайзинг строк (`toPlainText`);
- экземпляра `i18n` — получение текущей локали.

```typescript
import i18n from "@/i18n";
import { apiGet, type ApiResponse } from "./apiUtils";
import { toPlainText } from "./sanitizeUtils";
```

Тип `AvailableLocale` напрямую в `seoUtils.ts` не импортируется: он приходит через `ApiResponse`.

> Между `src/i18n.ts` и `src/utils/seoUtils.ts` существует циклический импорт: `i18n.ts` вызывает `updateSEO`, а `seoUtils.ts` обращается к `i18n`. Он безопасен, пока модули используют друг друга только внутри тел функций, а не на верхнем уровне. То же касается `apiUtils.ts`, который тоже импортирует `i18n`.

## Контракт API

### Эндпоинт

Полный путь формируется как `<base>api/v1/seo/{locale}.json`, где:

- `<base>` — базовый путь приложения из глобальной переменной `__APP_BASE__` (определена в `vite.config.ts`): `/` локально и `/vue3-starter-template/` в режиме `ghpages`;
- `{locale}` — код текущей локали (`ru`, `en`, `de`).

### Общий контракт `ApiResponse`

Определён в `apiUtils.ts` и общий для всех ответов API:

```typescript
export interface ApiResponse {
  language: AvailableLocale;
}
```

Слой `apiUtils` сравнивает `language` из ответа с текущей локалью `i18n` и бросает ошибку при несовпадении. Значение `language` в mock-файле должно совпадать с именем файла (`de.json` → `"de"`).

### Типы данных

#### SeoItem

```typescript
interface SeoItem {
  title: string;
  description: string;
  keywords: string;
}
```

Структура SEO-данных. Содержит три основных поля для базовой поисковой оптимизации. Тип внутренний.

#### SeoResponse

```typescript
interface SeoResponse extends ApiResponse {
  seo: SeoItem;
}
```

Полный ответ API: код языка (наследуется от `ApiResponse`) и сами SEO-данные. Тип внутренний, но используется в сигнатуре экспортируемой `fetchSeo`.

### Структура mock-данных

Для разработки и тестирования в директории `public/api/v1/seo/` размещаются JSON-файлы для каждого поддерживаемого языка. Пример `ru.json`:

```json
{
  "language": "ru",
  "seo": {
    "title": "Сеть детских спортивных клубов в Германии, Австрии и Швейцарии | Kidoo Club",
    "description": "Kidoo Club — это круглогодичный спорт для детей 4–14 лет. Футбол, плавание, лыжи, скалолазание, рафтинг и десятки других активностей. Один абонемент — сотни возможностей в Германии, Австрии и Швейцарии.",
    "keywords": "детский спортивный клуб Германия Австрия Швейцария, спорт для детей, секции для детей, детский фитнес, детский футбол, детские лыжи, активный отдых для детей, клуб для детей DACH"
  }
}
```

### Переход к production API

При переходе к реальному серверу структура ответов должна точно соответствовать mock-файлам, чтобы не менять код фронтенда. Нужно учесть три места:

- базовый адрес API (`API_BASE_URL` в `apiUtils`, который строится из `__APP_BASE__`);
- формат пути: в моках путь заканчивается на `.json`, а реальный API может использовать другой вид (например, `/api/v1/seo?locale=ru`). В этом случае придётся поправить и формирование пути в `fetchSeo`, а не только базовый адрес;
- наличие поля `language` в каждом ответе: без него проверка в `apiUtils` всегда будет завершаться ошибкой.

## Функции

### updateMetaTag (внутренняя)

```typescript
updateMetaTag(name: string, content: string): void
```

Обновляет содержимое существующего мета-тега или создаёт новый, если тега нет в DOM. Повторные вызовы не создают дубликатов.

**Параметры:**

- `name` (string) — имя мета-тега (значение атрибута `name`).
- `content` (string) — содержимое мета-тега (значение атрибута `content`).

**Возвращает:** `void`.

> Функция не экспортируется. Санитайзинг она сама не выполняет: он происходит выше, в `applySeo`.
>
> Функция ищет теги по атрибуту `name`. Теги Open Graph (`og:title`, `og:description`) используют атрибут `property`, поэтому через неё они не обновляются.

### applySeo (внутренняя)

```typescript
applySeo(seo: SeoItem): void
```

Применяет SEO-данные к странице. Для каждого значения вызывает `toPlainText` с ограничением длины:

- `document.title` — `toPlainText(seo.title, 200)`;
- `description` — `toPlainText(seo.description, 500)`;
- `keywords` — `toPlainText(seo.keywords, 500)`;
- атрибут `lang` у `<html>` — `i18n.global.locale.value`.

Является единственной точкой записи данных в документ, поэтому санитайзинг нельзя обойти случайно.

### fetchSeo

```typescript
fetchSeo(): Promise<SeoResponse>
```

Асинхронно получает SEO-данные с сервера. Для формирования endpoint использует текущую локаль `i18n.global.locale.value`: например, для русского языка выполняется запрос к `seo/ru.json` (полный путь строит `apiUtils`).

**Параметры:** отсутствуют.

**Возвращает:** `Promise<SeoResponse>`. Данные возвращаются «как есть», без санитайзинга: он выполняется только при применении к странице.

**Ошибки:** функция не перехватывает ошибки, а пробрасывает их вызывающему коду:

- `ApiError` с полями `status` и `statusText` — если сервер ответил HTTP-статусом 4xx или 5xx;
- `Error("Network or parsing error: …")` — сетевая ошибка или некорректный JSON;
- `Error("No data received from API")` — тело ответа пустое или не является объектом;
- `Error("API language mismatch: expected …, got …")` — язык ответа не совпадает с текущей локалью;
- `Error("Invalid SEO data received from API")` — в ответе нет блока `seo`.

**Пример:**

```typescript
try {
  const seoData = await fetchSeo();
  console.log(`Получены SEO-данные для языка: ${seoData.language}`);
} catch (error) {
  console.error("Ошибка при загрузке SEO-данных:", error);
}
```

### updateSEO

```typescript
updateSEO(): Promise<void>
```

Главная функция модуля. Получает SEO-данные через `fetchSeo()` и применяет их к странице с помощью `applySeo()`.

**Параметры:** отсутствуют.

**Возвращает:** `Promise<void>`: промис разрешается, когда все SEO-элементы обновлены (или когда запрос завершился ошибкой, см. ниже).

**Обновляемые элементы:**

- `document.title` — заголовок страницы (`data.seo.title`);
- `<meta name="description">` — описание страницы (`data.seo.description`);
- `<meta name="keywords">` — ключевые слова (`data.seo.keywords`);
- `<html lang="">` — атрибут языка документа из текущей локали i18n.

**Обработка ошибок:** внутри функции есть блок `try/catch`. При любой ошибке (сеть, статус, проверка контракта, отсутствие блока `seo`) она логируется в консоль с префиксом `Failed to update SEO tags:` и не пробрасывается дальше, поэтому сбой SEO не мешает работе приложения и смене языка. В этом случае теги остаются в прежнем состоянии.

**Пример:**

```typescript
i18n.global.locale.value = "de";
await updateSEO();
```

## Санитайзинг значений

Все строки, полученные по API, считаются недоверенными. Перед записью в документ их обрабатывает `toPlainText(value, maxLength)` из `src/utils/sanitizeUtils.ts`:

1. Не-строки (`null`, числа, объекты, `undefined`) превращаются в пустую строку.
2. Строка нормализуется в форму NFC.
3. Управляющие символы (`\p{Cc}`), мягкий перенос (`\u00AD`), символы нулевой ширины (`\u200B`, `\u2060`, `\uFEFF`) и bidi-переопределения и изоляторы (`\u202A-\u202E`, `\u2066-\u2069`) заменяются **пробелом**.
4. Любые последовательности пробельных символов схлопываются в один пробел, края обрезаются (`trim`). Результат всегда однострочный.
5. Длина ограничивается значением `maxLength`.

Что важно помнить:

- Это **не экранирование HTML**. Результат безопасен для `textContent`, `document.title` и `meta.content`, но его нельзя вставлять в `innerHTML`.
- ZWJ/ZWNJ (`\u200D`, `\u200C`) и метки LRM/RLM намеренно сохраняются: они нужны в легитимном тексте (например, в персидском языке и составных эмодзи).
- Если вместо строки придёт другой тип (скажем, число в `title`), то в `document.title` и тег попадёт пустая строка, а не `undefined`.

## Интеграция с системой локализации

### Автоматическое обновление при смене языка

Упрощённый пример `src/i18n.ts` (реальный код содержит дополнительные проверки, например защиту обращений к `localStorage`):

```typescript
import { updateSEO } from "@/utils/seoUtils";

export async function setLocale(locale: AvailableLocale) {
  if (!i18n.global.availableLocales.includes(locale)) {
    await loadLocaleMessages(locale);
  }
  i18n.global.locale.value = locale;
  localStorage.setItem("locale", locale);

  // Обновление SEO при смене языка (ошибки обрабатываются внутри updateSEO)
  await updateSEO();
}
```

Вызывать `updateSEO()` нужно после установки новой локали, иначе будут запрошены данные прежнего языка (а проверка `language` в `apiUtils` сразу же отвергнет такой ответ после смены локали).

> Если в `setLocale()` стоит `await updateSEO()`, то смена языка (и запуск приложения, если `initLocale()` использует `setLocale()`) ожидает ответ API. Чтобы SEO не задерживало интерфейс, вызов можно не ожидать: `void updateSEO();`.

### Инициализация при загрузке приложения

Если `initLocale()` применяет начальную локаль через `setLocale()`, SEO-данные загрузятся автоматически, отдельный вызов не нужен. Если локаль при старте устанавливается в обход `setLocale()`, `updateSEO()` нужно вызвать один раз в `src/main.ts`:

```typescript
import { createApp } from "vue";
import App from "./App.vue";
import i18n, { initLocale } from "./i18n";
import { updateSEO } from "./utils/seoUtils";

const app = createApp(App);
app.use(i18n);

initLocale()
  .catch(console.error)
  .finally(() => {
    app.mount("#app");
    void updateSEO();
  });
```

Не стоит дополнительно вызывать `updateSEO()` в `onMounted` корневого компонента, если `setLocale()` уже его вызывает: запрос выполнится дважды.

## Примеры использования

### Получение SEO-данных без применения к странице

```typescript
import { fetchSeo } from "@/utils/seoUtils";

async function preloadSeoData() {
  try {
    const seoData = await fetchSeo();

    // Предварительная валидация данных
    if (!seoData.seo.title || seoData.seo.title.length < 10) {
      console.warn("Заголовок страницы может быть слишком коротким для SEO");
    }

    return seoData;
  } catch (error) {
    console.error("Не удалось предзагрузить SEO-данные:", error);
    return null;
  }
}
```

> `fetchSeo()` возвращает сырые данные без санитайзинга. Если такие строки выводятся где-то ещё (например, в интерфейсе), их нужно пропустить через `toPlainText` из `@/utils/sanitizeUtils` и выводить только через `textContent` или интерполяцию `{{ }}`, а не через `v-html`.

### Ручное управление другими мета-тегами

`updateMetaTag` не экспортируется, поэтому для дополнительных тегов (`author`, `robots`, `theme-color` и др.) её нужно сначала экспортировать из `seoUtils.ts` (это возможное улучшение, в модуле пока не сделано). Если значения берутся из недоверенных источников, их нужно прогонять через `toPlainText`. Статические теги проще задать прямо в `index.html`.

## Обработка ошибок и отладка

### Типы ошибок

| Ошибка                                      | Где возникает           | Что происходит                                                             |
| ------------------------------------------- | ----------------------- | -------------------------------------------------------------------------- |
| Сетевая ошибка (нет соединения)             | `apiGet` → `fetchSeo()` | `Network or parsing error`; `updateSEO()` логирует и завершается           |
| HTTP-статус 4xx или 5xx                     | `apiGet` → `fetchSeo()` | `ApiError` со `status` и `statusText`; дальше то же                        |
| Некорректный JSON                           | `apiGet` → `fetchSeo()` | `Network or parsing error`; дальше то же                                   |
| Пустое тело или не объект                   | `apiGet` → `fetchSeo()` | `No data received from API`; дальше то же                                  |
| Ответ для другого языка                     | `apiGet` → `fetchSeo()` | `API language mismatch`; дальше то же                                      |
| Отсутствует блок `seo`                      | `fetchSeo()`            | `Invalid SEO data received from API`; дальше то же                         |
| Поле внутри `seo` отсутствует или не строка | `applySeo()`            | Не считается ошибкой: `toPlainText` вернёт пустую строку, тег получит `""` |

### Отладочная информация

Для отладки можно временно добавить логирование:

```typescript
import i18n from "@/i18n";
import { fetchSeo } from "@/utils/seoUtils";

async function debugSeoFetch() {
  console.log(`Запрос SEO-данных для языка: ${i18n.global.locale.value}`);

  try {
    const data = await fetchSeo();
    console.log("Получены SEO-данные:", data);
    return data;
  } catch (error) {
    // В строгом режиме TypeScript error имеет тип unknown
    console.error("Подробности ошибки SEO:", error);
    throw error;
  }
}
```

`ApiError` в `apiUtils` не экспортируется как класс: это интерфейс с полями `status` и `statusText`, поэтому проверка через `instanceof` не подойдёт. Ошибки такого вида отличаются наличием поля `status`:

```typescript
if (error instanceof Error && "status" in error) {
  console.error("HTTP-статус:", error.status);
}
```

## Ограничения и особенности

1. **Зависимость от сети.** Для получения SEO-данных нужно соединение с сервером (или с dev-сервером при использовании моков).
2. **Асинхронность.** Все публичные функции работы с SEO асинхронны.
3. **Нет собственного кеша.** Повторные запросы при смене языка зависят от HTTP-кеша браузера. Для статических JSON-файлов и реального API стоит продумать заголовки кеширования, иначе после обновления контента пользователи могут видеть старые данные.
4. **Нет fallback при ошибке.** При недоступности API теги не обновляются и остаются прежними, в том числе от предыдущего языка. Страховкой служат значения по умолчанию в `index.html`.
5. **Частичная валидация ответа.** Проверяются статус, тип тела, совпадение `language` и наличие блока `seo`. Типы полей `title`, `description` и `keywords` не проверяются: вместо `undefined` в теги попадёт пустая строка, а пустой `document.title` браузер заменит адресом страницы.
6. **Устаревшие ответы при быстрой смене языка.** Ожидаемая локаль читается в `apiUtils` уже после получения ответа, поэтому ответ на прежний язык отвергается ошибкой `API language mismatch` и не попадает в теги. Побочный эффект: такой отброшенный запрос оставляет запись об ошибке в консоли. Запросы при этом не отменяются.
7. **Клиентский рендеринг.** Боты без исполнения JS видят только `index.html`. Для полноценной индексации и превью ссылок нужен SSR, SSG или пререндер.
8. **Только атрибут `name`.** `updateMetaTag` не подходит для Open Graph и Twitter Cards (`property`).
9. **Мета-тег `keywords`.** Google его не учитывает, основное значение имеют `title` и `description`.
10. **Индивидуальное SEO для страниц.** Функция `updateSEOWithKeys` удалена. Данные для разных страниц нужно получать через отдельные эндпоинты или параметры запроса.
11. **Обрезка по длине.** `slice` в `toPlainText` считает единицы UTF-16 и может разрезать суррогатную пару (например, эмодзи) на границе лимита.
12. **Санитайзинг не заменяет экранирование.** См. [Санитайзинг значений](#санитайзинг-значений).

## Возможные улучшения

Пока это предложения, в модуле они не реализованы.

**Запоминать локаль в момент отправки запроса** (или передавать её в `apiGet` явным параметром) и отменять устаревшие запросы через `AbortController`. Тогда не будет ложных ошибок `API language mismatch` в консоли при быстрой смене языка.

**Валидация типов полей**, чтобы не получать пустой заголовок молча:

```typescript
const { title, description, keywords } = data.seo;

if (
  typeof title !== "string" ||
  typeof description !== "string" ||
  typeof keywords !== "string"
) {
  throw new Error("Некорректный формат SEO-данных");
}
```

**Устанавливать `lang` до запроса**, чтобы атрибут не зависел от доступности API.

**Параметр локали**: `fetchSeo(locale = i18n.global.locale.value)` упростит тестирование и предзагрузку данных для других языков.

**Теги Open Graph**: дополнительный параметр или отдельная функция для атрибута `property`, а также `canonical` и `hreflang`.

**Улучшения в `apiUtils`:**

- выставлять `Content-Type` только при наличии `body`: у GET-запроса он не нужен и при запросах на другой домен вызывает preflight;
- собирать заголовки через `new Headers(options.headers)`, чтобы корректно работали экземпляры `Headers` и массивы пар;
- добавить `Array.isArray(data)` в проверку тела ответа, если контракт предполагает объект;
- вынести `declare const __APP_BASE__: string;` в общий `env.d.ts`.

**Тесты** (Vitest + jsdom):

- `toPlainText`: не-строки, `\n` и `\t`, bidi-символы, сохранение ZWJ/ZWNJ, нормализация, обрезка;
- `seoUtils`: применение тегов, отсутствие дубликатов при повторных вызовах и поведение при ошибке API (с подменой `apiGet`).

## Миграция с версии на переводах i18n

Раньше SEO-тексты хранились в блоке `seo` файлов `src/locales/`, а `updateSEO()` была синхронной. Что изменилось:

- Блок `seo` из `src/locales/*.json` удалён, данные берутся из `public/api/v1/seo/{locale}.json`.
- Добавлена глобальная переменная `__APP_BASE__` (`vite.config.ts`) для корректных путей на GitHub Pages.
- `updateSEO()` стала асинхронной. Её вызов можно ожидать через `await`, ошибки обрабатываются внутри функции.
- Функция `updateSEOWithKeys` и константа `SEO_KEYS` сначала были помечены `@deprecated`, а после проверки новой схемы удалены: индивидуальные данные для страниц теперь должны приходить с сервера.
- Все значения теперь проходят через `toPlainText` с ограничением длины.
- Функция `updateMetaTag` перестала экспортироваться.

**Было:**

```typescript
updateSEO(); // синхронный вызов
```

**Стало:**

```typescript
await updateSEO(); // асинхронный вызов, ошибки логируются внутри
```

## Совместимость

- **Vue I18n**: 9.0+ в режиме Composition API (`legacy: false`). Используется только для получения текущей локали.
- **TypeScript**: 4.0+. Для регулярного выражения с `\p{...}` и флагом `u` (в `sanitizeUtils`) рекомендуется `target` не ниже ES2018.
- **Браузеры**: все современные браузеры с поддержкой Fetch API и ES2018+ (Unicode property escapes в регулярных выражениях).

## Связанные файлы

- `src/utils/apiUtils.ts` — утилиты для выполнения API-запросов, общий контракт `ApiResponse` и проверка языка ответа.
- `src/utils/sanitizeUtils.ts` — санитайзинг недоверенных строк (`toPlainText`).
- `src/i18n.ts` — конфигурация интернационализации и вызов `updateSEO()` при смене языка.
- `vite.config.ts` — определение глобальной переменной `__APP_BASE__`.
- `public/api/v1/seo/*.json` — mock-файлы с SEO-данными для разработки.
- `index.html` — значения `<title>`, `description` и `lang` по умолчанию.
