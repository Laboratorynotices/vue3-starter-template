# Vue 3 Starter Template

Современный стартовый шаблон для разработки веб-приложений на **Vue 3** с использованием **TypeScript**, **Vue I18n** с ленивой загрузкой переводов интерфейса и локализованного контента, динамическим обновлением SEO-тегов при смене языка, а также системой мокирования API-запросов на основе статических JSON-файлов.

Шаблон предназначен для быстрого создания новых проектов с заранее подготовленной архитектурой, базовой конфигурацией и необходимыми инструментами для комфортной разработки и дальнейшего масштабирования приложения.

## Описание проекта

**Vue 3 Starter Template** — это базовая заготовка для разработки современных SPA-приложений (Single Page Application) на Vue 3.

Основная цель шаблона — избавить разработчика от необходимости повторно настраивать стандартную инфраструктуру при создании каждого нового проекта.

Вместо того чтобы начинать разработку с пустого репозитория, можно использовать уже подготовленную основу, которая включает:

- Настроенную среду разработки на базе Vite.
- Поддержку TypeScript.
- Организованную файловую структуру.
- Алиас `@` для коротких и устойчивых к рефакторингу импортов.
- Поддержку мультиязычности через Vue I18n.
- Ленивую загрузку переводов технических текстов интерфейса (`src/locales/`).
- Автоматическое определение языка и запоминание выбора пользователя.
- Динамическое обновление SEO-тегов (`<title>`, `description`, `keywords`) и атрибута `lang` при смене языка (`src/utils/seoUtils.ts`).
- Динамическую загрузку локализованного контента.
- Систему мокирования API на основе статических JSON-файлов.
- Единое автоматическое форматирование кода с помощью Prettier.
- Разделение логики приложения, компонентов и сервисов.
- Конфигурацию для разработки и production-сборки.

Шаблон не привязан к конкретной предметной области и может использоваться как основа для административных панелей, пользовательских интерфейсов, внутренних корпоративных систем и других веб-приложений.

## Использование в новых проектах

Шаблон рассчитан на многократное использование в качестве основы для новых приложений.

### Вариант 1. Создание проекта через GitHub Template

2. Используй функцию **Use this template**.
3. Укажи название нового репозитория.
4. Создай репозиторий на основе шаблона.
5. Клонируй созданный репозиторий локально.
6. Установи зависимости и запусти приложение.

### Вариант 2. Клонирование репозитория

```bash
git clone <repository-url> my-new-project
cd my-new-project
npm install
```

После клонирования рекомендуется выполнить следующие действия:

1. Изменить название проекта в `package.json`.
2. Обновить метаданные приложения.
3. Обновить тег `<title>` в файле `index.html` (см. заметку ниже).
4. Проверить настройки переменных окружения.
5. Настроить базовый URL приложения.
6. Удалить демонстрационные страницы и ненужные компоненты.
7. Добавить необходимые бизнес-модули.
8. Настроить поддерживаемые языки (`SUPPORT_LOCALES` в `src/i18n.ts` и файлы в `src/locales/`).
9. Заменить демонстрационный перевод `hello` и тестовую кнопку переключения языка в `src/components/HelloWorld.vue`.
10. Заменить временные SEO-тексты (блок `seo` в файлах `src/locales/`) на реальные заголовок, описание и ключевые слова проекта на каждом поддерживаемом языке.
11. Адаптировать содержимое `public/api/v1/` под структуру API нового приложения.

> **Не забыть обновить `<title>`.** После загрузки файлов шаблона нужно заменить тег `<title>` в файле `index.html`, записав в него хотя бы будущее название конкретного проекта.
>
> Заголовок страницы, полученный через SEO-механизм (сейчас из блока `seo` файлов локалей, в дальнейшем — через API-запросы), подставляется уже после выполнения скриптов. А `index.html` отдаётся браузеру раньше, поэтому в первый момент загрузки будет виден стоковый заголовок из шаблона. Чтобы пользователь не видел заглушку, `<title>` в `index.html` должен содержать актуальное название проекта. По той же причине в `index.html` стоит прописать значения по умолчанию для `description` и `lang` (на основном языке сайта): их увидят роботы, которые не исполняют JavaScript.

## Архитектура приложения

При разработке рекомендуется придерживаться принципа разделения ответственности.

Каждая часть приложения должна выполнять свою определённую функцию:

- **Views** отвечают за отображение страниц.
- **Components** содержат переиспользуемые элементы интерфейса.
- **Composables** инкапсулируют повторно используемую реактивную логику.
- **Services** обеспечивают взаимодействие с API.
- **I18n** (`src/i18n.ts` и `src/locales/`) отвечает за управление активной локалью, переводы технических текстов интерфейса и их ленивую загрузку.
- **SEO** (`src/utils/seoUtils.ts`) отвечает за применение локализованных SEO-данных к документу: `<title>`, мета-теги и атрибут `lang`.
- **Types** содержат общие определения типов.
- **Utils** содержат вспомогательные функции.
- **Public API** предоставляет статические JSON-ответы для имитации backend и локализованный контент.

Такое разделение позволяет уменьшить связанность между модулями и упрощает поддержку приложения по мере увеличения его функциональности.

## Алиас для импортов

В шаблоне настроен алиас `@`, который всегда указывает на каталог `src`. Он позволяет писать импорты от корня исходного кода, не используя длинные цепочки вида `../../../`.

Было:

```typescript
import heroImg from "../assets/hero.png";
```

Стало:

```typescript
import heroImg from "@/assets/hero.png";
```

Такой импорт читается проще и не ломается при переносе файла в другую папку, так как не зависит от расположения импортирующего файла.

### Как это настроено

Алиас нужно объяснить двум независимым потребителям: Vite (разрешает пути при разработке и сборке) и TypeScript (проверка типов и подсказки в редакторе). Чтобы не дублировать настройки, алиас описан один раз в `tsconfig.app.json`, а Vite читает его оттуда.

`tsconfig.app.json`:

```json
{
  // ...
  "compilerOptions": {
    // ...

    /* Aliases */
    "paths": {
      "@/*": ["./src/*"]
    }
  }
}
```

`vite.config.ts`:

```typescript
// ...

export default defineConfig({
  // ...
  resolve: {
    tsconfigPaths: true,
  },
});
```

> Показаны только добавленные фрагменты, многоточия изображают остальное содержимое файлов.

Алиас описан в `tsconfig.app.json`, а не в корневом `tsconfig.json`, потому что конфигурация TypeScript разделена на части. Файл `tsconfig.app.json` относится к коду приложения (`src`), а алиас нужен только ему.

### Использование

Алиас используется в блоках `<script>` компонентов и в обычных `.ts`-файлах:

```typescript
import HelloWorld from "@/components/HelloWorld.vue";
```

### Добавление нового алиаса

При необходимости в раздел `paths` можно добавить дополнительные алиасы, например:

```json
"paths": {
  "@/*": ["./src/*"],
  "@components/*": ["./src/components/*"]
}
```

Для большинства проектов достаточно одного общего `@`, он проще и понятнее.

### Примечания

- После изменения `vite.config.ts` или `paths` dev-сервер лучше перезапустить, чтобы изменения гарантированно подхватились.
- Опция `resolve.tsconfigPaths` доступна не во всех версиях Vite. Если в используемой версии её нет, можно подключить плагин [`vite-tsconfig-paths`](https://github.com/thebuilder/vite-tsconfig-paths) или описать алиас вручную через [`resolve.alias`](https://vite.dev/config/shared-options#resolve-alias) (тогда его придётся продублировать в `tsconfig.app.json`).
- В документации Vite отмечено, что эта возможность влечёт накладные расходы на производительность, а команда TypeScript не рекомендует использовать `paths` для изменения поведения внешних инструментов. Для стартового шаблона это не критично, но стоит помнить при росте проекта.
- Опция не применяется внутри `.less`-файлов. Если в проекте появятся препроцессоры стилей, алиасы для них придётся настраивать отдельно. Также стоит отдельно проверить использование `@/` в CSS и в путях к ресурсам внутри шаблонов Vue (например, `<img src="@/assets/...">`).
- Алиас действует только на импорты в коде. На URL-адреса запросов к моковому API (`/api/v1/...`) он не влияет.
- При подключении тестов, ESLint-плагинов для импортов и других инструментов нужно проверить, что они понимают алиас.

## Локализация (I18n)

Для управления локалью приложения и перевода интерфейса используется [Vue I18n](https://vue-i18n.intlify.dev/).

Архитектура локализации построена на разделении двух видов текстов:

- **Технические тексты (интерфейс)** — подписи кнопок, элементов управления, сообщения об ошибках и другие короткие строки. Их переводы хранятся в JSON-файлах `src/locales/` и подключаются через Vue I18n (функция `$t`).
- **Содержание сайта** — SEO-данные, заголовки, описания, контент страниц, навигация. Оно поступает через API из `public/api/v1/` и не дублируется в `src/locales/`. Временное исключение: пока API-запросы не реализованы, SEO-тексты лежат в блоке `seo` файлов `src/locales/` (см. раздел [SEO-данные и мета-теги](#seo-данные-и-мета-теги)).

Vue I18n отвечает за управление активной локалью, загрузку и применение переводов интерфейса. Содержание сайта загружается отдельно, в зависимости от активной локали.

### Основные принципы

- Поддерживаемые языки определяются централизованно в `src/i18n.ts` (массив `SUPPORT_LOCALES`).
- Список доступных локалей является статическим.
- Переводы интерфейса хранятся отдельно для каждого языка: один JSON-файл на локаль в `src/locales/`. Набор ключей во всех файлах должен совпадать.
- Переводы загружаются лениво: динамический импорт подгружает файл языка только тогда, когда он нужен (code splitting).
- Выбранный язык сохраняется в `localStorage`. Если хранилище недоступно (приватный режим, запрет в настройках браузера, переполнение квоты), язык всё равно переключается, а в консоль выводится предупреждение.
- Начальный язык определяется по приоритету: сохранённый выбор пользователя, затем язык браузера, затем язык по умолчанию.
- При каждой смене языка обновляются SEO-теги (`<title>`, `description`, `keywords`) и атрибут `lang` элемента `<html>`: `setLocale()` вызывает `updateSEO()` из `src/utils/seoUtils.ts`.
- Приложение монтируется только после инициализации локали (`initLocale()` в `src/main.ts`), чтобы пользователь не видел ключей вместо текста.
- Содержание сайта (страницы, SEO, навигация) хранится в API-ресурсах в `public/api/v1/` и не смешивается с переводами интерфейса (временное исключение для SEO-текстов описано выше).

### Конфигурация языков

Список поддерживаемых языков определяется в `src/i18n.ts`:

```typescript
export const SUPPORT_LOCALES = ["de", "ru", "en"] as const;

export type AvailableLocale = (typeof SUPPORT_LOCALES)[number];

export const DEFAULT_LOCALE: AvailableLocale = "de";
```

Модификатор `as const` превращает массив в readonly-кортеж с литеральными значениями, поэтому тип `AvailableLocale` выводится из него автоматически (`"de" | "ru" | "en"`). Язык по умолчанию — немецкий: он же служит запасной локалью (`fallbackLocale`).

### Переводы интерфейса

Переводы технических текстов лежат в `src/locales/`:

```text
src/
└── locales/
    ├── de.json
    ├── en.json
    └── ru.json
```

Имя файла должно совпадать с кодом локали из `SUPPORT_LOCALES`. Пример `src/locales/de.json`:

```json
{
  "hello": "Hallo"
}
```

Использование в шаблоне компонента:

```vue
<p>{{ $t("hello") }}</p>
```

Функция `$t` доступна в шаблонах глобально (включена опция `globalInjection`), дополнительный импорт не требуется.

Правила для файлов переводов:

- Набор ключей во всех файлах должен быть одинаковым, иначе в одном из языков пользователь увидит запасной перевод или сам ключ.
- Это правило распространяется и на временный блок `seo`: он должен присутствовать в файлах всех локалей, иначе в заголовке вкладки может оказаться строка `seo.title`.
- JSON не допускает комментариев и «висячих» запятых.
- Файлы сохраняются в кодировке UTF-8.
- В сообщениях Vue I18n специальное значение имеют символы `{`, `}`, `@`, `$` и `|` (подстановки, ссылки на другие сообщения, множественные формы). Чтобы использовать их буквально, их нужно экранировать.

### Модуль `src/i18n.ts`

Модуль экспортирует константы, типы и функции для работы с локалью:

| Экспорт                                                | Назначение                                                                                                            |
| ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `SUPPORT_LOCALES`, `AvailableLocale`, `DEFAULT_LOCALE` | Список поддерживаемых локалей, производный тип и локаль по умолчанию                                                  |
| `isValidLocale(code)`                                  | Type guard: проверяет, что строка является поддерживаемой локалью                                                     |
| `loadLocaleMessages(locale)`                           | Динамически импортирует `src/locales/<locale>.json` и регистрирует сообщения в i18n                                   |
| `setLocale(locale)`                                    | Загружает переводы (если нужно), переключает локаль, сохраняет выбор, обновляет SEO-теги и `lang` через `updateSEO()` |
| `getNextLocale()`                                      | Возвращает следующую локаль из списка с циклическим переходом                                                         |
| `switchLocale()`                                       | Переключает на следующую локаль (de → ru → en → de)                                                                   |
| `getPrimaryNavigatorLocale()`                          | Возвращает язык браузера, если он поддерживается, иначе язык по умолчанию                                             |
| `getLocaleFromLocalStorage()`                          | Возвращает сохранённую валидную локаль или `null`                                                                     |
| `getInitialLocale()`                                   | Определяет начальную локаль по приоритету                                                                             |
| `initLocale()`                                         | Определяет и применяет начальную локаль при старте приложения                                                         |
| `default` (экземпляр `i18n`)                           | Экземпляр Vue I18n для подключения через `app.use(i18n)`                                                              |

Экземпляр Vue I18n создаётся в режиме Composition API (`legacy: false`) с пустым набором сообщений: переводы подгружаются динамически.

### Подключение к приложению

Интеграция выполняется в `src/main.ts`:

```typescript
import { createApp } from "vue";
import "./style.css";
import App from "./App.vue";
import i18n, { initLocale } from "./i18n";

const app = createApp(App);
app.use(i18n);

initLocale()
  .catch(console.error)
  .finally(() => app.mount("#app"));
```

Приложение монтируется после завершения `initLocale()`, и при успехе, и при ошибке: если загрузка переводов не удалась, ошибка выводится в консоль, но приложение всё равно запускается.

### Использование в компонентах

Для проверки в шаблон добавлен тестовый фрагмент в `src/components/HelloWorld.vue`:

```vue
<script setup lang="ts">
import { switchLocale } from "@/i18n";
</script>

<template>
  <div>
    <p>{{ $t("hello") }}</p>
    <button @click="switchLocale">Switch language</button>
  </div>
</template>
```

Кнопка последовательно переключает язык: de → ru → en → de. Этот фрагмент демонстрационный, в реальном проекте его нужно заменить (подпись кнопки тоже должна браться из переводов).

### Организация локализованных данных

Локализованное содержание сайта (в отличие от переводов интерфейса) располагается в отдельных директориях внутри `public/api/v1/`.

Пример:

```text
public/
└── api/
    └── v1/
        ├── seo/
        │   ├── ru.json
        │   ├── en.json
        │   └── de.json
        │
        ├── pages/
        │   ├── ru.json
        │   ├── en.json
        │   └── de.json
        │
        └── navigation/
            ├── ru.json
            ├── en.json
            └── de.json
```

Каждый файл содержит локализованный контент для соответствующего языка.

### Загрузка локализованных данных

Для получения контента используются стандартные API-запросы.

Например, для загрузки SEO-данных на русском языке:

```typescript
const response = await fetch("/api/v1/seo/ru.json");

if (!response.ok) {
  throw new Error("Failed to load SEO data");
}

const seoData = await response.json();
```

При переключении языка приложение запрашивает соответствующие ресурсы для новой локали.

> Этот пример описывает целевую схему. Пока SEO-данные не подключены к API, `src/utils/seoUtils.ts` берёт их из блока `seo` файлов `src/locales/` (см. раздел [SEO-данные и мета-теги](#seo-данные-и-мета-теги)).

### Добавление нового языка

Для подключения дополнительного языка необходимо:

1. Добавить его языковой код в массив `SUPPORT_LOCALES` в `src/i18n.ts` (тип `AvailableLocale` обновится автоматически).
2. Создать файл `src/locales/<код>.json` с тем же набором ключей, что и в остальных языках (включая временный блок `seo`).
3. Добавить соответствующие JSON-файлы в `public/api/v1/`.
4. Убедиться, что для нового языка присутствуют все необходимые переводы интерфейса и API-ресурсы.

Таким образом, конфигурация поддерживаемых языков и переводы интерфейса остаются частью приложения, а локализованное содержание сайта отделено от исходного кода и загружается через API.

### Примечания

- Динамический `import()` с именем локали в пути (`./locales/${locale}.json`) обрабатывается Vite: он требует относительный путь и явное расширение файла. Каждый JSON-файл попадает в сборку отдельным чанком.
- Если TypeScript не принимает импорт JSON, нужно проверить в `tsconfig.app.json` опцию `resolveJsonModule` (при `moduleResolution: "bundler"` она включена по умолчанию).
- Импорт `@/i18n` в компонентах работает благодаря алиасу `@` (см. раздел [Алиас для импортов](#алиас-для-импортов)).
- `fallbackLocale` равна `DEFAULT_LOCALE`, но переводы загружаются только для выбранной локали. Если в выбранном языке нет какого-то ключа, а немецкий словарь ещё не загружен, будет показан сам ключ. Поэтому набор ключей во всех файлах должен совпадать.
- Между `src/i18n.ts` и `src/utils/seoUtils.ts` существует циклический импорт (`i18n.ts` импортирует `updateSEO`, а `seoUtils.ts` импортирует экземпляр `i18n`). Он безопасен, пока оба модуля обращаются друг к другу только внутри тел функций, а не на верхнем уровне (см. раздел [SEO-данные и мета-теги](#seo-данные-и-мета-теги)).
- Код `src/i18n.ts` рассчитан на клиентское SPA: он обращается к `localStorage`, `navigator` и `document`. При переходе на SSR или пререндеринг инициализацию придётся переработать. То же относится к `src/utils/seoUtils.ts`, который работает с `document`.
- Для поисковых систем языковые версии лучше отдавать на отдельных адресах (например, `/de/`, `/ru/`, `/en/`), а не только через `localStorage`.

## SEO-данные и мета-теги

Локализованные SEO-данные (заголовок вкладки, описание, ключевые слова и язык документа) применяются к странице модулем `src/utils/seoUtils.ts`. Это обычный TypeScript-модуль без привязки к компонентам: он обращается к `i18n.global`, а не к `useI18n()`, поэтому доступен из любого места проекта.

Что обновляется при смене языка:

| Элемент документа            | Источник данных                           |
| ---------------------------- | ----------------------------------------- |
| `<title>` (`document.title`) | перевод по ключу `seo.title`              |
| `<meta name="description">`  | перевод по ключу `seo.description`        |
| `<meta name="keywords">`     | перевод по ключу `seo.keywords`           |
| `<html lang="">`             | текущая локаль `i18n.global.locale.value` |

### Временное хранение SEO-текстов

Пока API-запросы не реализованы, SEO-тексты хранятся в блоке `seo` файлов локалей `src/locales/`. Пример `src/locales/ru.json`:

```json
{
  "seo": {
    "title": "Заголовок сайта",
    "description": "Описание сайта",
    "keywords": "ключевые слова"
  }
}
```

Блок `seo` добавляется к существующим переводам как ещё один ключ верхнего уровня. Аналогичные записи с соответствующими переводами нужно добавить в `en.json` и `de.json`. Структура блока во всех файлах должна быть одинаковой.

После подключения API (`public/api/v1/seo/`) этот блок должен быть удалён из `src/locales/`, а данные для `seoUtils.ts` начнут поступать из ответов API.

### Модуль `src/utils/seoUtils.ts`

| Элемент                                                       | Назначение                                                                                                                  |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `SEO_KEYS` (не экспортируется)                                | Константа с ключами переводов SEO (`seo.title`, `seo.description`, `seo.keywords`)                                          |
| `updateMetaTag(name, content)` (не экспортируется)            | Находит `<meta name="...">` или создаёт его и записывает `content`, поэтому дубликатов при повторных вызовах не возникает   |
| `updateSEOWithKeys(titleKey?, descriptionKey?, keywordsKey?)` | Обновляет `title`, `description`, `keywords` и `lang` по переданным ключам переводов (по умолчанию используются `SEO_KEYS`) |
| `updateSEO()`                                                 | Обновляет SEO по глобальным ключам сайта; вызывается при смене языка                                                        |

Функция `updateSEOWithKeys` с пользовательскими ключами предназначена для страниц с индивидуальными SEO-данными, например `updateSEOWithKeys("pages.about.seo.title", ...)`.

### Подключение к смене языка

Функция `updateSEO()` вызывается в `setLocale()` в файле `src/i18n.ts` после того, как новая локаль установлена (и после загрузки языкового пакета, если он подгружается лениво). В противном случае в тегах окажутся тексты прежнего языка. В `src/i18n.ts` для этого добавляется импорт:

```typescript
import { updateSEO } from "@/utils/seoUtils";
```

### Проверка

1. Запустить проект и открыть DevTools на вкладке Elements.
2. Убедиться, что в `<head>` есть `<meta name="description">` и `<meta name="keywords">`, а у `<html>` корректный `lang`.
3. Переключить язык и убедиться, что заголовок вкладки, содержимое тегов и `lang` изменились.
4. Переключить язык несколько раз подряд и проверить, что дубликатов мета-тегов нет.

### Примечания

- **Режим Vue I18n.** Выражение `i18n.global.locale.value` корректно только в режиме Composition API (`legacy: false`), в котором создан экземпляр `i18n` в этом шаблоне. В legacy-режиме `locale` является строкой, и `.value` вернёт `undefined`.
- **Циклический импорт.** `seoUtils.ts` импортирует `@/i18n`, а `i18n.ts` импортирует `seoUtils.ts`. Это работает, пока `updateSEO()` и `setLocale()` не вызываются на верхнем уровне модуля `i18n.ts` до создания экземпляра `i18n`. Если это станет проблемой, можно передавать `i18n` в утилиту аргументом или вместо прямого вызова из `setLocale()` использовать `watch(i18n.global.locale, updateSEO)`.
- **Первичная установка.** Вызов в `setLocale()` срабатывает при каждой установке локали. Если при старте приложения локаль устанавливается в обход `setLocale()` (например, только через `createI18n({ locale })`), SEO-данные до первого переключения останутся статичными. В этом случае нужно один раз вызвать `updateSEO()` при инициализации.
- **Значения по умолчанию в `index.html`.** Поисковые роботы и боты, которые не исполняют JavaScript, увидят только исходный HTML. Для них в `index.html` нужны `<title>`, `description` и `lang` на основном языке сайта.
- **Ограничения SPA.** Динамические мета-теги учитывают пользователи и Googlebot (он исполняет JS), но не краулеры соцсетей и мессенджеров, строящие превью ссылок. Для них нужен SSR, SSG или пререндер. Из лёгких вариантов стоит рассмотреть [`@unhead/vue`](https://unhead.unjs.io/).
- **Мета-тег `keywords`.** Google его не учитывает, реальный вес имеют `title` и `description`. Ориентиры по длине: заголовок до 50–60 символов, описание около 150–160.
- **Open Graph и Twitter Cards.** `updateMetaTag` ищет теги по атрибуту `name`, а Open Graph (`og:title`, `og:description`) использует `property`. Для них потребуется отдельная функция или параметр. Заодно в будущем можно добавить `<link rel="canonical">` и `hreflang`.
- **Индивидуальное SEO страниц.** Ключи можно хранить в `route.meta` (например, `meta: { seo: { titleKey: "..." } }`) и вызывать `updateSEOWithKeys` в `router.afterEach`, а при отсутствии ключей откатываться к глобальным.
- **Типизация ключей.** Параметры `titleKey`, `descriptionKey`, `keywordsKey` имеют тип `string`, поэтому опечатка обнаружится только в рантайме (в заголовке окажется сам ключ). При строгой типизации схемы сообщений vue-i18n тип ключей можно ограничить.
- **Тесты.** Утилита хорошо проверяется модульно (Vitest + jsdom): достаточно вызвать `updateSEO()` и проверить `document.title`, мета-теги и `lang`, а также отсутствие дубликатов при повторных вызовах.

## Мокирование API

Для разработки интерфейса без готового backend предусмотрено использование статических JSON-файлов, расположенных в директории `public/api/v1`.

Данный подход позволяет имитировать ответы сервера посредством обычных HTTP-запросов, не поднимая отдельный backend-сервер и не используя сложные механизмы перехвата запросов.

### Основные преимущества

- Простая организация моковых данных.
- Отсутствие необходимости в отдельном mock-сервере.
- Использование стандартных HTTP-запросов.
- Возможность имитации различных API-эндпоинтов.
- Простое переключение между моковым и реальным API.
- Независимость моковых данных от исходного TypeScript-кода.

### Организация мок-файлов

```text
public/
└── api/
    └── v1/
        ├── seo/
        │   ├── ru.json
        │   ├── en.json
        │   └── de.json
        │
        ├── pages/
        │   ├── ru.json
        │   ├── en.json
        │   └── de.json
        │
        ├── users/
        │   └── ...
        │
        └── products/
            └── ...
```

Каждый JSON-файл представляет собой имитацию ответа определённого API-эндпоинта.

### Пример моковых данных

`public/api/v1/users/users.json`

```json
[
  {
    "id": 1,
    "name": "John Doe",
    "email": "john@example.com"
  },
  {
    "id": 2,
    "name": "Jane Doe",
    "email": "jane@example.com"
  }
]
```

### Получение моковых данных

Поскольку Vite предоставляет содержимое директории `public` как статические ресурсы, JSON-файлы доступны по соответствующим URL.

Например:

```text
/api/v1/seo/ru.json
/api/v1/seo/en.json
/api/v1/pages/ru.json
/api/v1/users/users.json
/api/v1/products/products.json
```

Для получения данных используется стандартный `fetch`:

```typescript
const response = await fetch("/api/v1/users/users.json");

if (!response.ok) {
  throw new Error("Failed to fetch users");
}

const users = await response.json();
```

### Имитирование API-эндпоинтов

При необходимости можно организовать структуру файлов таким образом, чтобы она соответствовала структуре реального API.

Например:

```text
public/
└── api/
    └── v1/
        ├── users/
        │   ├── index.json
        │   └── profile.json
        │
        └── products/
            ├── index.json
            └── details.json
```

Соответствующие URL:

```text
/api/v1/users/index.json
/api/v1/users/profile.json
/api/v1/products/index.json
/api/v1/products/details.json
```

**Важно:** статические JSON-файлы подходят для имитации фиксированных ответов на GET-запросы. Они не реализуют серверную бизнес-логику, обработку POST/PUT/DELETE, динамическую фильтрацию или изменение данных. Для такой функциональности потребуется отдельный mock-сервер либо другой механизм мокирования.

## Работа с API

Для взаимодействия с backend рекомендуется использовать отдельный слой сервисов.

Это позволяет изолировать HTTP-запросы от компонентов и централизованно управлять обработкой ответов сервера.

Рекомендуемая структура:

```text
services/
├── api.ts
├── user.service.ts
└── product.service.ts
```

Пример сервиса:

```typescript
export interface User {
  id: number;
  name: string;
  email: string;
}

export async function fetchUsers(): Promise<User[]> {
  const response = await fetch("/api/v1/users/users.json");

  if (!response.ok) {
    throw new Error("Failed to fetch users");
  }

  return response.json() as Promise<User[]>;
}
```

Сервис подключается в компоненте или composable через алиас `@` (см. раздел [Алиас для импортов](#алиас-для-импортов)):

```typescript
import { fetchUsers } from "@/services/user.service";
```

В дальнейшем при подключении реального backend достаточно изменить адрес API или способ получения данных в сервисном слое, сохранив интерфейсы взаимодействия с компонентами.

## Форматирование кода

Для единого стиля кода используется [Prettier](https://prettier.io/). Он автоматически приводит к общему виду файлы `.vue`, `.ts`, `.js`, `.json`, `.css` и другие, поэтому стиль не зависит от настроек конкретного редактора или разработчика, а диффы в Git содержат только смысловые изменения.

### Конфигурация

- `.prettierrc` — конфигурация Prettier. Файл содержит пустой объект `{}`, то есть используются значения по умолчанию: длина строки 80 символов, двойные кавычки, точки с запятой. Чтобы изменить стиль, достаточно дописать параметры в этот файл (например, `"singleQuote": true` или `"printWidth": 100`). Полный список параметров — в [документации Prettier](https://prettier.io/docs/options).
- `.prettierignore` — список файлов и папок, которые форматировать не нужно. По умолчанию это `dist` (результат сборки Vite) и `coverage` (отчёты о покрытии тестами). Папка `node_modules` игнорируется автоматически. Если в `vite.config.ts` изменён `build.outDir`, список нужно скорректировать.

Prettier установлен как dev-зависимость с точной версией (без префикса `^`). Это защищает от ситуации, когда после обновления зависимостей форматирование неожиданно меняется на сотнях строк.

### Запуск

Форматирование всего проекта выполняется командой:

```bash
npm run format
```

Она запускает скрипт из раздела `scripts` файла `package.json`:

```json
"scripts": {
  "format": "prettier . --write"
}
```

> Показан только добавленный ключ, остальные скрипты (`dev`, `build`, `preview` и другие) остаются на своих местах.

То же самое можно выполнить напрямую, без скрипта:

```bash
npx prettier . --write
```

Чтобы только проверить код, ничего не изменяя (например, в CI), используется флаг `--check`:

```bash
npx prettier . --check
```

### Форматирование при сохранении в VS Code

1. Установить расширение **Prettier - Code formatter** (`esbenp.prettier-vscode`). Оно использует Prettier, установленный в проекте, поэтому версия в редакторе совпадает с версией в терминале.
2. Открыть настройки (`Ctrl+,`, на macOS `Cmd+,`), включить **Editor: Format On Save** и выбрать **Prettier - Code formatter** в пункте **Editor: Default Formatter**.

То же самое через JSON-настройки (`Preferences: Open User Settings (JSON)` или `Preferences: Open Workspace Settings (JSON)` для настроек только этого проекта):

```json
{
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "esbenp.prettier-vscode"
}
```

Если файлы `.vue` форматируются другим расширением, Prettier можно назначить явно:

```json
{
  "[vue]": {
    "editor.defaultFormatter": "esbenp.prettier-vscode"
  }
}
```

Чтобы расширение не трогало проекты без собственной конфигурации, в пользовательских настройках можно добавить `"prettier.requireConfig": true`.

Если форматирование при сохранении не срабатывает, нужно проверить, что Prettier выбран форматировщиком для данного типа файла, что файл не указан в `.prettierignore` и что на вкладке **Output** (канал **Prettier**) нет ошибок.

### Правила работы с форматированием

- Первый прогон Prettier по существующему коду затрагивает много файлов, поэтому его нужно выполнять **отдельным коммитом** без смысловых правок.
- Параметры в `.prettierrc` нужно менять до массового форматирования. Иначе проект придётся переформатировать повторно, тоже отдельным коммитом.
- После первого прогона стоит проверить `git status` и убедиться, что Prettier не изменил lock-файл и другие сгенерированные файлы. Если изменил, их нужно добавить в `.prettierignore`.
- Хеш коммита с массовым форматированием можно записать в файл `.git-blame-ignore-revs`, чтобы он не мешал `git blame`.
- Если в проект будет добавлен ESLint, правила стиля, конфликтующие с Prettier, нужно отключить (пакет `eslint-config-prettier`).

## Рекомендации по разработке

### TypeScript

- Использовать строгую типизацию.
- Избегать `any`, если можно определить конкретный тип.
- Выносить общие интерфейсы и типы в отдельные файлы.
- Типизировать ответы API.

### Vue

- Использовать Composition API.
- Предпочитать `<script setup lang="ts">`.
- Разделять бизнес-логику и представление.
- Выносить повторяющуюся логику в composables.
- Использовать переиспользуемые компоненты.

### Архитектура

- Не размещать API-запросы непосредственно в компонентах.
- Хранить моковые JSON-ответы в `public/api/v1`.
- Использовать сервисный слой для взаимодействия с API.
- Не смешивать бизнес-логику и получение данных.
- Поддерживать логическую структуру каталогов.

### Импорты

- Для импортов из разных каталогов использовать алиас `@/` вместо длинных относительных путей (`../../`).
- Относительные пути (`./`) допустимы для файлов, лежащих рядом.
- Новые алиасы добавлять только в `tsconfig.app.json`, чтобы настройка оставалась в одном месте.
- После изменения `paths` перезапускать dev-сервер.

### Локализация

- Не размещать тексты интерфейса непосредственно в шаблонах: использовать `$t("ключ")` и переводы из `src/locales/`.
- В `src/locales/` хранить только технические тексты (интерфейс), а содержание сайта — в API-ресурсах `public/api/v1/`. Единственное временное исключение — блок `seo`, который нужно убрать после подключения API.
- Поддерживать одинаковый набор ключей во всех файлах `src/locales/` (включая блок `seo`) и одинаковую структуру данных для всех локалей в API.
- Проверять наличие необходимых ресурсов для каждого поддерживаемого языка.
- Централизованно управлять списком доступных локалей через `SUPPORT_LOCALES` в `src/i18n.ts`.
- Переключать язык только через функции модуля `src/i18n.ts` (`setLocale`, `switchLocale`), чтобы сохранение выбора и обновление SEO-тегов и атрибута `lang` не пропускались.
- Не изменять `document.title`, мета-теги и атрибут `lang` напрямую: использовать `updateSEO()` и `updateSEOWithKeys()` из `src/utils/seoUtils.ts`.
- Не обращаться к `localStorage` из компонентов напрямую: работа с хранилищем должна оставаться внутри модуля локализации или (после рефакторинга) в отдельной утилите.

### Форматирование

- Не форматировать код вручную, а полагаться на Prettier.
- Включить форматирование при сохранении в редакторе.
- Запускать `npm run format` перед коммитом, если автоформатирование в редакторе не включено.
- Не смешивать массовое форматирование и смысловые правки в одном коммите.

## Сборка проекта

Для создания production-версии приложения используется:

```bash
npm run build
```

Результат сборки обычно располагается в директории:

```text
dist/
```

Эта директория указана в `.prettierignore`, поэтому Prettier не форматирует результат сборки.

Файлы из `public/api/v1` автоматически копируются в production-сборку с сохранением структуры каталогов.

Таким образом, при стандартной конфигурации Vite моковые данные будут доступны по тем же URL и после сборки приложения.

Переводы интерфейса из `src/locales/` в копируемые статические файлы не попадают: они подключаются динамическим импортом, и Vite выделяет каждый язык в отдельный чанк, который загружается только при первом использовании этой локали. Временные SEO-тексты (блок `seo`) лежат в тех же файлах, поэтому загружаются вместе с переводами нужного языка.

Алиас `@` работает на этапе сборки так же, как и в режиме разработки: Vite заменяет его реальными путями, поэтому в итоговой сборке никаких дополнительных настроек не требуется.

Для корректной работы Vue Router при использовании HTML5 History Mode сервер должен быть настроен на возврат `index.html` для неизвестных маршрутов приложения.
